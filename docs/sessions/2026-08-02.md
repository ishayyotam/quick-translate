## 1. Core problem (root cause, not symptoms)

This was a green-field build, not a bugfix session on existing code — but the recurring *class* of defect across nearly every fix was the same root cause:

**The app pivots all cross-language logic through a single English word, then tries to verify that auxiliary API calls (example sentences, gender, synonyms) still refer to the same *sense* of that word as the one being displayed — and every bug came from that verification being either absent or too loose.**

Concretely:
- Google's MT/dictionary endpoints are **sense-blind at the word level**: querying an English word returns dictionary/example/synonym data for *all* its senses mixed together (e.g. "maiden" = girl (noun) AND unmarried (adjective); "solution" = fix-for-a-problem AND chemical-mixture AND business-offering).
- A naive substring match between "the German word we're displaying" and "a translated example sentence" produces false positives when a different sense's conjugated/inflected form happens to contain the target word as a lowercase substring (`"Essen"` (noun, food) ⊂ `"gegessen"` (verb form, ate) — case-insensitive match, wrong).
- The fix pattern that emerged and should be reused for any future cross-checking logic: **match case-sensitively** (German capitalizes nouns, so this alone discriminates noun-sense from verb-sense in most cases), and **verify against the actually-displayed word**, not the raw query.

Secondary root cause (one-time, now closed): the PWA's service worker used cache-first with a `CACHE_NAME` that never changed between deploys, so `sw.js` was never re-fetched/byte-compared and installed clients never saw updates. Fixed by switching to network-first (see §3).

## 2. Strategy / rules agreed on going forward

- **No build step, no framework, no dependencies.** Plain HTML/CSS/JS, deployed as static files via GitHub Pages. Keep it this way — do not introduce a bundler/npm unless explicitly asked.
- **Every "nice-to-have" enrichment (gender, example, synonyms) must fail silently and never block the core 3-way translation.** Core translation (EN/HE/DE text) must always render even if all enrichment calls fail.
- **Every async enrichment must guard against staleness** by re-checking `wordInput.value.trim() === originalText` before writing to the DOM (not a request-id counter — see §3, e6d0d5f, for why the counter approach was insufficient).
- **Sense-matching must be case-sensitive** wherever we're trying to confirm a German noun form appears in generated text. Do not "fix" a missing-match bug by lowercasing both sides — that's what caused the "gegessen" bug in the first place.
- **Mobile keyboards auto-capitalize and fire spurious duplicate `input` events.** Any new input-handling code must account for both (lowercase before querying case-sensitive dictionary endpoints; dedupe identical consecutive queries).
- **Manual language override (tap a card label) is the answer to cross-language homograph ambiguity** (e.g. "Gift" = present in English, poison in German; "Baum" = tree in German, surname-like ambiguity in auto-detect). Do not try to solve this with smarter auto-detection — the UI escape hatch is the intended design.
- GitHub Pages sits behind an edge cache (`Cache-Control: max-age=600`) independent of our service worker. After a push, the *origin* has the new file within seconds (verify with a cache-busting query string), but the bare URL can lag up to ~10 min. This is expected, not a deploy failure.

### 0e66ba7 — Fix service worker to actually pick up updates
**What broke:** `sw.js` `CACHE_NAME` was never bumped between deploys, and the fetch handler was cache-first (`caches.match(req).then(cached => cached || fetch(req))`). Since `sw.js`'s own bytes never changed, the browser's SW update-check never detected a new version, so installed clients (phone PWA) never re-fetched `app.js`/`index.html` after a deploy.
**Fix:**
- `sw.js:1` — bumped `CACHE_NAME` to `"quick-translate-v2"`.
- `sw.js:28–45` — fetch handler rewritten to network-first (try network, cache the response, fall back to cache only on failure). `translate.googleapis.com` requests are still bypassed entirely (never cached) — `sw.js:32`.
- `app.js:363–376` — added `serviceworker.controllerchange` listener that does a one-time `window.location.reload()` when a new SW takes control, so an already-open tab/PWA self-updates instead of silently running stale JS until manually closed.
**Caveat discovered later:** a page that already has *old* `app.js` loaded (from before this fix existed) can never run the *new* reload-listener code, because that code wasn't in the JS it already loaded. One-time manual reload was needed to bootstrap out of that state; not an ongoing issue.

### e6d0d5f — Fix German example being cancelled by spurious mobile input events
**What broke:** Android/Gboard fires extra `input` events for unchanged text (autocorrect/predictive-text finalization). The example-fetch path is 2 sequential network round-trips (slower than the instant 3-way translate), so it was much more likely to still be in-flight when a spurious duplicate event incremented the global `requestId` counter — which `updateGermanExample`'s cancellation check compared against, causing it to discard a perfectly valid in-flight result.
**Fix:**
- `app.js:36` — added `lastQueriedText`.
- `app.js:48–54` — debounced input handler now skips re-triggering `translate()` if the value is identical to the last one actually queried.
- Cancellation check inside the async enrichment functions changed from `requestId !== myRequestId` to `wordInput.value.trim() === originalText` (the "stillCurrent" pattern, still in use — see `app.js:138`, `198`, `293`). This means a harmless duplicate event for *unchanged* text no longer discards in-flight results, but a genuine text change still correctly aborts stale ones.

### 3f7deae — Fix example sentences missing for capitalized words
**What broke:** `dt=ex` (and `dt=bd`, `dt=ss`) dictionary/example lookups are case-sensitive and frequently have no entry for a capitalized word (`"Gift"` → 0 results, `"gift"` → 5 results) — confirmed via direct `curl`. Mobile text inputs auto-capitalize the first letter by default, so this silently broke the feature for nearly all real phone usage.
**Fix:**
- `app.js:122` (`fetchCandidateExamples`) — `.toLowerCase()` before querying. Same pattern later applied to `fetchGenderArticle` (app.js:172), `fetchDictionaryGroups` (app.js:214), `fetchEnglishSynonymGroups` (app.js:242).
- `index.html:21` — added `autocapitalize="off"` on the `<input>` so typed words aren't silently altered in the first place (defense in depth, not a substitute for the `.toLowerCase()` calls — both are required, see §6 invariants).

### fb604c9 — German noun gender tags (first version) + first example sense-verification attempt

### 5b35f63 — Fix example sentences matching the wrong sense (case-sensitivity) + enable for German-sourced input
**What broke:** `updateGermanExample`'s match check lowercased both the target word and the candidate translation before `.includes()`. `"Essen"` (noun, food) lowercased to `"essen"`, which *is* a substring of `"gegessen"` (a conjugated form of the unrelated verb `"essen"`, to eat) — false positive, wrong example shown (`"sie hatten gegessen und geschlafen"` for the noun "food"). Exact same failure class as the earlier "maiden" bug, via a different path.
**Fix:**
- `app.js:157–162` — match is now case-sensitive: `r.translated.includes(germanWord)` (no `.toLowerCase()` on either side). This works correctly for both cases: a capitalized noun target only matches the capitalized form (fixes the bug), while a lowercase verb target (e.g. user typed `"essen"` directly, German-sourced) still correctly matches lowercase conjugated forms like `"gelaufen"`/`"gegessen"` since those genuinely demonstrate the same verb.
- `updateGermanExample`'s signature dropped the `sourceLang` gate parameter entirely (was `(sourceLang, englishWord, germanWord, originalText)`, now `(englishWord, germanWord, originalText)`, app.js:131) — previously restricted to only run when `sourceLang === "en" || "he"` per the original feature request; now runs for German-sourced input too, since the underlying mechanism (pivot through `results[en].translated`) works regardless of source language.

### 5235c0e — Split English synonym clusters instead of merging
**What changed (not a bug fix, a quality improvement):** `synonymGroupsToPairs` (app.js:249–266) previously flattened+deduped all `dt=ss` clusters within a POS group into one blended word list. Discovered that each cluster is often a genuinely distinct sense (e.g. "solution" noun → 3 clusters: `answer/result/resolution...` (problem-solving), `services/work/resource(s)...` (business), `mixture/mix/blend...` (chemical)) that merging was hiding. Now each cluster renders as its own line (capped at 6 lines total, 6 words per cluster). Trade-off: words with many closely-related senses (e.g. "house") now show up to 6 lines instead of one — accepted as reasonable since the panel is opt-in (behind a collapsed toggle).

## 5. Key architecture notes for a future AI

- **5 files, no build step:** `index.html`, `style.css`, `app.js`, `manifest.json`, `sw.js`, plus `icon-192.png`/`icon-512.png`. Everything is plain script-tag JS — no modules, no bundler, no npm/package.json.
- **Data layer is a single undocumented Google endpoint:** `https://translate.googleapis.com/translate_a/single?client=gtx&sl=<src>&tl=<tgt>&dt=<flags>&q=<text>`. No API key, no auth, works via plain `fetch()`, no CORS issues observed. This is the same reverse-engineered endpoint browser extensions commonly use — **not** Anthropic/Google's official Cloud Translation API. It has no uptime/rate-limit guarantees and could change shape or break without notice; that fragility is inherent to the whole app.
- **Reverse-engineered response shapes** (all discovered empirically via `curl`, not documented anywhere):
  - `dt=t` → `data[0]` = array of `[translatedChunk, originalChunk, ...]`; join `chunk[0]` for full text. `data[2]` = detected source language code.
  - `dt=ex` (examples) → `data[13][0]` = array of `[sentenceWithBoldTags, ...]`.
  - `dt=bd` (dictionary/back-translation) → `data[1]` = array of groups `[partOfSpeech, flatWordArray, entriesArray, sourceWord, rank]`; each entry in `entriesArray` = `[word, glossArray, null, weight, article?]` — `article` (`der`/`die`/`das`) only present on German noun entries.
  - `dt=ss` (thesaurus) → **`data[11]`** (verified by literal array enumeration — easy to mis-count as `data[10]`, see 66c21b3). Groups = `[partOfSpeech, clustersArray, sourceWord, rank]`; each cluster = `[wordArray, dictRef, tags?]`.
  - `dt=md` (definitions) — fetched/inspected during investigation but **not currently used** in the app (see §6, unresolved #1).
  - All of the above share the same underlying dictionary reference-ID scheme (e.g. `"m_en_gbus0967340.006"`) across `md`/`ex`/`ss`/`bd` — in principle cross-referenceable for exact sense alignment, but the app currently only does heuristic (cluster/case-sensitive-substring) matching, not ID-based alignment.
- **Concurrency idiom ("stillCurrent" pattern):** every async enrichment function takes `originalText` and internally defines `const stillCurrent = () => wordInput.value.trim() === originalText`, checking it before every DOM write. This replaced an earlier request-id-counter approach that was too eager to cancel (see e6d0d5f). **Any new async enrichment feature should follow this exact pattern** — canonical example: `updateGermanGender`, `app.js:192–207`.
- **All enrichments are fire-and-forget** from `translate()` (`app.js:348–350`) — not awaited, each fails silently (empty catch blocks) so a broken enrichment never blocks or errors the core 3-way translation.
- **`LANGS = ["en", "he", "de"]`** (`app.js:1`) — order is relied upon via `LANGS.indexOf(...)` throughout for indexing the parallel `results` array from `Promise.all(LANGS.map(...))`. Do not reorder without auditing every `indexOf` call site.
- **Deployment:** push to `master` → GitHub Pages (source = branch `master`, path `/`, configured via `gh api repos/ishayyotam/quick-translate/pages`) auto-rebuilds. Origin updates within seconds of push; the public URL can lag ~10 min behind due to GitHub's edge CDN cache (`Cache-Control: max-age=600`) — verify a fresh deploy landed by hitting the file with a cache-busting query string (`?bust=<timestamp>`) before assuming something's broken.
- **Local dev:** `python -m http.server 3001` from inside `translate-app/`. Also registered as a `translate-app` entry in `~/.claude/launch.json` for the Browser-pane preview tool — note the `npx serve`-based config failed in this environment (path-quoting issue with the space in `C:\Users\Yotam Ishay`), so it was switched to `python -m http.server --directory`.
- **git note:** `translate-app/` has its own independent `.git` (via `git init` inside the folder) — the parent home directory (`C:\Users\Yotam Ishay\`) is *also* a separate git repo; these are unrelated, don't conflate them.

## 6. Unresolved issues

1. **No exact sense-to-translation alignment.** The shared dictionary reference-ID scheme across `md`/`ex`/`ss`/`bd` (see §5) is identified but not implemented. Current sense-splitting (5235c0e) is heuristic (cluster-level), not precise. Status: open enhancement, not blocking.
2. **"maiden"/`עלמה` never shows an example sentence.** Root-caused, not a code bug: all 4 available `dt=ex` examples for "maiden" translate to `"Jungfrau"`, never `"Mädchen"` (verified via direct `curl` against every candidate). Genuine gap in Google's underlying dictionary data. Status: won't-fix, documented/expected.
3. **`גידם` (Hebrew, "armless person") mistranslates as "bitten".** Verified via direct `curl` against the raw API (bypassing our code entirely) that this is Google's own NMT model output for this specific rare/archaic Hebrew word, not something introduced by our code. Status: won't-fix, upstream MT quality limitation.
4. **Android home-screen widget** — explicitly requested, then descoped by the user after being told it requires a separate native Android app (Kotlin/Java `AppWidgetProvider`), not achievable as a PWA extension. Current mitigation is the installed PWA icon (manifest.json). Status: deferred; would be a new, separate project if revisited.
5. **Claude Code mobile remote-control connection is broken** (unrelated to this codebase). Phone shows "Remote control session is offline"; user ran `/remote-control` on the laptop to restart it, phone still shows messages sending (greyed out) then reverting/failing. Not fixable from within this session/repo — flagged to the user as likely needing Anthropic support escalation. Status: open, out of scope for this project.
6. **Browser-pane `computer{action:"screenshot"}` tool was unreliable/timed out repeatedly this session.** Environmental/tooling issue, not an app defect — all verification this session was done via `get_page_text` / `javascript_exec` DOM inspection instead. Worth knowing for the next session so time isn't wasted retrying screenshots.

## 7. Locked values / invariants — must never change without re-reading this doc

- **`app.js:157–161` case-sensitive match** (`r.translated.includes(germanWord)`, no `.toLowerCase()`) — reintroducing case-insensitivity here reintroduces the "gegessen" bug class. This is deliberate, not an oversight.
- **`.toLowerCase()` before querying `dt=ex`/`dt=bd`/`dt=ss`** (`app.js:122, 172, 214, 242`) combined with **`autocapitalize="off"`** (`index.html:21`) — both required together; the dictionary/thesaurus/example endpoints are case-sensitive and largely indexed under lowercase common-word forms.
- **`sw.js` fetch handler must stay network-first** (or `CACHE_NAME` must be bumped every deploy if ever reverted to cache-first) — this is what makes future deploys actually reach installed clients. See 0e66ba7 for the full failure mode if this regresses.
- **`dt=ss` payload is at `data[11]`**, not `data[10]` — easy off-by-one, verified by literal enumeration, see §5.
- **The "stillCurrent" staleness-guard pattern** (compare `wordInput.value.trim()` to the `originalText` snapshot, not a global counter) is required for any new async enrichment — the counter-based approach was tried and found insufficient (e6d0d5f).
- **`LANGS = ["en", "he", "de"]` order** — indexed via `.indexOf()` throughout; do not reorder without auditing all call sites.
- **Example-sentence feature scope**: runs for *any* source language now (post-5b35f63), not just EN/HE — do not reintroduce the `sourceLang` gate without checking whether that was actually intentional at the time (it was explicitly removed per user request).
- **`translate.googleapis.com` requests are never cached by the service worker** (`sw.js:32`, explicit early-return bypass) — must stay this way; caching translation results would serve stale/wrong translations offline.
